# NoteWiki 编辑加载与保存保护设计

## 问题与目标

`html/wiki/notewiki.html` 在单篇文章首次点“编辑”时，存在异步读取与编辑器初始化交错的路径。编辑器可能暂时显示空内容或加载占位文本；在此状态点击保存时，保存逻辑还可能先从 Vditor 同步出未完成的值，导致服务端被空内容或旧内容覆盖。

目标是保证：

1. 当前文章的服务端内容加载完成前，编辑器不会接受编辑或发起保存。
2. 只有当前这次编辑加载请求可以写入编辑器，过期请求不得覆盖当前内容。
3. 正常加载完成后，保存提交的内容必须来自当前编辑器，不改变现有的空文章合法性。
4. 读取失败时保留明确失败状态并阻止覆盖性保存。

## 设计

### 编辑加载状态

在前端维护一个递增的编辑加载序号，并为每次 `loadEditorFromArticleId` 保存当前文章 ID 和序号。开始读取时：

- `_contentLoaded = false`；
- 编辑文本框和保存按钮进入不可操作状态；
- Vditor 只接收“加载中”显示值，不把它当作用户输入；
- 发起 `/api/wiki-read` 请求。

响应或异常到达时，先验证序号仍是当前请求且 `S.editId` 未变化。过期响应直接忽略。只有 `data.ok` 的当前响应才写入正文、设置 `_contentLoaded = true` 并解除编辑锁；失败响应保持未加载状态，解除文本框锁但保持保存按钮禁用，并显示错误信息。

### Vditor 初始化

Vditor 的延迟加载继续保留。初始化值取当前文本框的待显示值，初始化回调只刷新当前值，不触发 `onEditorInput`。在 `_contentLoaded` 为 false 时，`syncVditorToTextarea` 不得把 Vditor 的占位值写回文本框；服务端内容成功到达后再执行一次单向刷新。

### 保存保护

`_doSave` 的第一步是检查当前编辑是否仍处于可保存状态，检查顺序早于任何 Vditor 同步：

- 非新建文章且 `_contentLoaded` 为 false：直接返回，不请求 `/api/wiki-save`；
- 当前编辑状态无效或文章 ID 已变化：直接返回；
- 加载完成后才同步 Vditor、读取标题/分类/正文并提交。

保存按钮状态与上述状态同步。新建文章不依赖服务端读取，因此仍允许保存空正文；已有文章即使正文本来就是空字符串，只要读取成功也允许保存空字符串。

### 请求响应隔离

读取请求和保存请求的异步回调都验证编辑上下文。旧文章的响应只能结束自己的请求，不能修改当前文章的标题、正文、基线、备份或保存状态。这样可同时覆盖首次打开和后续切换场景。

## 错误处理

- HTTP/JSON 读取异常：显示“读取文章失败”，保持 `_contentLoaded = false`，禁止保存。
- 服务端返回 `ok: false`：显示服务端错误，禁止保存。
- Vditor 脚本加载失败：保留 Markdown 编辑路径的可用性；如果当前选择的是 Vditor，则显示加载失败并保持保存保护，不提交占位内容。
- 正常保存成功后，按现有逻辑更新文章列表、编辑基线和本地备份。

## 测试策略

项目没有现成的前端测试框架，因此增加一个可由 PowerShell/Node 执行的轻量回归脚本，提取并运行 NoteWiki 的核心编辑状态函数，使用可控 Promise 验证：

1. 读取尚未完成时点击保存不会调用 `/api/wiki-save`。
2. 当前文章读取成功后保存提交服务端返回的正文。
3. 读取失败后不能以空正文覆盖原文章。
4. 过期读取响应不会覆盖当前文章内容。

同时运行 JavaScript 语法检查、已有测试、`make` 构建；不修改 `src` 后端逻辑，因为问题边界在浏览器端异步状态管理。
